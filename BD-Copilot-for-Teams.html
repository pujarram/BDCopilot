System architecture

Two flows share one brain. An indexing pipeline keeps a vector store current with everything in SharePoint and Teams; a query pipeline answers a Teams chat message by reading that same store — but only after checking, for that specific user, that they're allowed to see each source. That check is what makes the rest of this safe to build.

Why security trimming happens twice

Indexing stores each chunk's SharePoint ACL as metadata, but access changes constantly — someone leaves a team, a file gets restricted. Trusting a stale permission copied in at index time is the most common way these systems leak. The API re-checks the live ACL through Graph on every single query, before any chunk reaches the model.

Where this differs from the brief

The original outline is sound end-to-end; a few sequencing and componentry calls are worth flagging before anyone starts building:

Provider-agnostic model layer

Rather than calling Ollama or Azure OpenAI directly from application code, put an abstraction in front of both — Microsoft's Semantic Kernel (native .NET, first-class Azure OpenAI support, and an Ollama connector) is the natural fit here. The rest of the API then talks to one interface; switching environments is a config change, not a code change. This is what makes the Settings screen in the prototype meaningful rather than cosmetic.

Delta queries, not full rescans

"Scan Teams files" only scales once. Microsoft Graph's delta query (GET /drives/{id}/root/delta) returns just what changed since the last sync token, so the Document Sync Service can run every few minutes instead of crawling the whole tenant nightly. A full crawl still runs once, on onboarding, to seed the index.

Start on pgvector, graduate to Azure AI Search

pgvector is the right choice for the prototype and pilot — it's free, fast enough at the pilot's scale, and keeps everyone in one Postgres instance alongside the metadata table already in the brief. Azure AI Search earns its cost once security-trimmed search, semantic ranking, and multi-tenant scale actually matter — that's a Phase 4 migration, not a day-one requirement.

Draft, don't publish

Every generator in the prototype produces a reviewable draft, never a final file sent anywhere. A wrong number in a generated business case is a much worse failure mode than a slow one; a human approving before export is the cheapest guardrail available.

Local ⇄ production, side by side

Local Ollama

  • Runs entirely on the developer's machine
  • Zero token cost while iterating on prompts
  • No customer data ever leaves the laptop
  • Good enough to prove retrieval quality and UX flows

Production Azure OpenAI

  • Deployed inside the same Entra ID tenant as the data
  • Enterprise content filtering & regional residency
  • Higher-quality generation for client-facing documents
  • Usage metered per model deployment for cost governance

The swap is one setting, resolved at startup by Semantic Kernel's connector registration:

// appsettings.{Development,Production}.json
{
  "Ai": {
    "Provider": "Ollama", // or "AzureOpenAI"
    "Ollama": { "Endpoint": "http://localhost:11434", "Model": "llama3.1:8b" },
    "AzureOpenAI": { "Endpoint": "https://bd-copilot.openai.azure.com", "Deployment": "gpt-4o" }
  }
}

Rollout plan

Five phases, each one shippable and demoable on its own. Nothing in Phase 0 or 1 requires Teams or Azure OpenAI at all — that's deliberate, so the hardest part (retrieval quality) gets proven before the most expensive parts (enterprise integration, production model spend) are switched on.

Ideas worth adding to the brief

A feedback loop on generated content

Every accept, edit, or discard of a generated section is a labelled example of what "good" looks like for this team. Logging that quietly from day one — without slowing anyone down to rate anything explicitly — is what eventually lets the RFP Generator learn this team's actual voice instead of a generic one.

An evaluation harness before scale, not after

A small, hand-picked set of real questions with known-correct source documents, re-run on every change to chunking, embeddings, or prompts. Fifteen minutes to build in Phase 1; the only reliable way to know a "small tweak" didn't quietly make retrieval worse.

Cost and usage visibility from the first production query

Token spend on GPT-4o/GPT-5 for long document generation adds up quickly across a BD team. Logging tokens-per-request against team and initiative in Application Insights from Phase 2 onward means the first cost conversation happens with data, not a surprised finance review.

Treat the Document Library as a trust surface, not just a status page

The library screen in this prototype doubles as the easiest way for a team to notice indexing has silently stalled, or that a file they expected to be searchable is showing "restricted." Making that visible — rather than only surfacing errors in logs — is cheap now and expensive to retrofit later.

This is a working prototype of the interface and a proposed build sequence, not a finished product — the buttons that generate documents in the Prototype tab simulate the flow described here rather than calling a real model or Graph API. Swap in your own sample proposals and the demo data in Chat, Knowledge Search and the Document Library becomes a true internal pilot.
